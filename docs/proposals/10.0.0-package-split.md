# Proposal: split the package for 10.0.0

Status: draft, for discussion. Nothing here ships in 9.x.

## The problem, measured

`@smartledger/bsv` is currently a Bitcoin library, a W3C VC-JWT toolkit, a
DID:web resolver, a legal-token protocol and an attestation framework in one
install. The cost is paid by everyone, including the majority who want one of
those things.

Requiring the root to get `Script`:

| | modules | time | heap |
|---|---|---|---|
| `require('@smartledger/bsv')` | 129 | 270ms | 12.7MB |
| `require('@smartledger/bsv/lib/script')` | 24 | 106ms | — |

Per subsystem, loaded alone:

| subsystem | modules |
|---|---|
| `lib/script` | 24 |
| `lib/transaction` | 40 |
| `lib/covenant` | 43 |
| `lib/ltp` | 48 |
| `lib/smart_contract` | 62 |
| `lib/gdaf` | 65 |

Two things make this worse than the numbers suggest:

1. **Nothing tree-shakes.** `index.mjs` is a named-export wrapper over the CJS
   build, so a bundler that sees `import { Script }` still pulls GDAF and LTP
   into the browser bundle. The subpaths in `exports` are the only escape, and
   they are not what the README teaches.
2. **The npm listing has to describe all of it.** A BSV script developer
   searching npm reads a description that leads with legal tokens and
   credentials. The audience most likely to adopt is the one least addressed.

The subpath exports already work and already carry the fix. What is missing is
that the *default* path is the expensive one.

## Shape

Five packages, one repository, published together.

| package | contains | approx modules |
|---|---|---|
| `@smartledger/bsv-core` | keys, addresses, script, transaction, block, SPV, crypto, encoding | ~45 |
| `@smartledger/bsv-script` | `SmartContract`, covenants, OP_PUSH_TX, PELS, ordinals, NotaryHash, script helper | ~62 |
| `@smartledger/bsv-crypto` | ECIES, Message, Mnemonic, Shamir | ~30 |
| `@smartledger/bsv-vc` | DID:web, VC-JWT, StatusList, GDAF, Anchor | ~65 |
| `@smartledger/bsv-ltp` | Legal Token Protocol | ~48 |
| `@smartledger/bsv` | **meta-package**: depends on all five, re-exports everything | unchanged |

The meta-package is the whole compatibility story. `require('@smartledger/bsv')`
keeps returning exactly what it returns today, including the ~74 flat
convenience functions (`createDID`, `prepareRightToken`, …) that currently sit
at top level. Nobody's install moves.

## Sequencing

The split is a breaking change for anyone who deep-requires `lib/**`, and it
cannot share a release with a stability promise. It also must not become the
seventh major in a year. So:

**9.x (now → 2027-09-01)** — nothing changes. Optionally, the new packages are
published *additively* during this window: `bsv-core` and `bsv-script` go out as
real packages, `@smartledger/bsv` starts depending on them internally, and its
public surface is unchanged. Consumers who want the small thing can adopt early;
consumers who do nothing notice nothing. The API surface guard
(`test/api_surface.js`) proves the surface held.

**10.0.0 (2027-09 or later)** — the meta-package remains and keeps working. What
breaks is only:

- deep requires past the declared `exports` (already excluded by STABILITY.md)
- the three near-duplicate ~1041KB bundles, if they are dropped in the same
  release

**Never** — removing the meta-package. It costs almost nothing to maintain once
the split exists, and removing it would strand every existing install for no
benefit.

## What this fixes that subpaths alone do not

Subpath exports already let a careful consumer load 24 modules instead of 129.
Three things they cannot fix:

1. **The default.** Most consumers write `require('@smartledger/bsv')` because
   that is what the README shows. Making the small package a separate install
   makes the cheap path the obvious one.
2. **npm positioning.** A package can only have one description and one keyword
   set. `bsv-script` can say "OP_PUSH_TX covenants and an interpreter-verified
   script engine" without competing with credentials for the same 15 keywords.
3. **Tree-shaking.** Separate packages can ship real ESM with `sideEffects:
   false`, which the current CJS-wrapper cannot.

## Open questions

- **Do `bsv-core` and `bsv-script` merge?** The script engine is the
  differentiator and splitting it from `Transaction` may be an artificial line —
  a covenant author needs both. Merging gives one ~62-module package that is
  still less than half the current root. I lean toward merging.
- **Version alignment.** Lockstep versioning across all six is simplest to
  reason about and wastes version numbers on packages that did not change.
  Independent versioning is more honest and much harder to support. Lockstep
  is probably right for a team this size.
- **The three ~1041KB bundles.** `bsv.min.js`, `bsv.bundle.js` and
  `bsv-gdaf.min.js` are byte-comparable supersets. They are documented CDN
  entries, so removing them breaks floating `@latest` URLs — which is why they
  survive 9.x untouched. 10.0.0 is the moment to consolidate, with the old names
  kept as redirects for one major if the CDN allows it.
- **Does the credential CLI move?** `bin/cli.js` is mostly credential
  workflows. It probably belongs with `bsv-vc`, which means the meta-package
  either loses the `smartledger-bsv` binary or keeps a thin shim.

## What would make this a bad idea

Worth stating plainly, because the answer might be no.

Six packages is six release processes, six changelogs and a lockfile matrix, for
a maintainer count in the low single digits. If the credentials and LTP
subsystems have real users who install the root package deliberately — not
incidentally — then the current arrangement is serving them and the only genuine
problem is npm positioning, which a rewritten description already improved.

Before committing to this, the number worth having is **how many installs use
only the Bitcoin surface**. If that is most of them, split. If the install base
is genuinely using credentials alongside Bitcoin primitives, keep one package,
fix the ESM wrapper so it tree-shakes, and stop there.
